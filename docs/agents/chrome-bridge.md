# Chrome bridge

Read this before touching `ChromeBridge*`, `ChromeControlTool`, `ChromeBridgePolicy`, `ChromeBridgeToken` or `chrome-extension/`.

- **The extension drives the operator's own signed-in browser**, so a page the agent opens is a page opened as the operator. Every rule below exists because the agent's reach is the operator's.
- **Policy lives on the JClaw side, never in the extension.** `ChromeBridgePolicy.visitRefusal` judges every navigation, and `ChromeControlTool` judges a tab again by its current address before it reads from it or acts on it, because a click can leave an allowed site. A read whose final address is off the list is discarded.
- **Loopback, private-network, malformed and credentialed URLs stay blocked even with allow-all.** The operator's browser is signed in to JClaw itself, so an agent reaching `localhost:9000` there would act as the operator. `SsrfGuard.assertUrlSafe` is the check; do not relax it for the main agent.
- **The allowlist and both overrides are `agent.<name>.chromeBridge.*` config rows.** They ride `AgentDeletionCascade` and the rename path for free, and only the operator-only `POST /api/config` writes them, so an agent cannot widen its own reach through `jclaw_api`. The two overrides are refused for any agent but `main` at write time (`ChromeBridgePolicy.rejectionFor`) and ignored for any other agent at read time, so a planted key does nothing.
- **A click goes through the approval gate unless the extension's `read` flagged the element a plain link**, via `Tool.dangerous(argsJson, agent)`, an agent-aware overload so only `main` can be exempt. A plain link is an `<a>` with an `href` that is not `javascript:`. Everything else is dangerous: buttons, form controls, a `<div>` with a click handler, and a ref never read. That is deliberately stricter than "is a form button", because a script-driven control sends data without a form. **`chrome_control` is also `neverRunsUnasked()`, so `DangerousActionGate.offChannelDecision` refuses such a click under `tool.approval.offChannelPolicy=allow` instead of letting it run.** Only `ask` (confirm in the bound Telegram DM) lets one through; `deny` refuses as it does for every tool; a standing grant still covers it. Before this rule the default `allow` ran it, and a non-main agent's click on a real enrollment form's submit button would have gone through; verified live. The model sees the shared generic denial text, so the gate's log line is where the reason lives. Link flags are kept per agent (`agent:tab:ref`), so one agent's read does not classify another's click. Still not caught: a link whose GET changes state, and a link whose own script posts on click. `type` cannot submit, since the tool has no key press. The allowlist is the real boundary.
- **The extension uses the `debugger` API (CDP) for real input.** A scripted DOM event is untrusted: a synthetic Enter does not submit a form, so key presses, coordinate clicks, hover, drag, background-tab screenshots and the console and network buffers all go through `chrome.debugger`, which also shows Chrome's debugging bar. `groupedTab` is the only thing keeping that to the JClaw group, so every action calls it first and every tool action pre-checks the tab's address; `everyNewActionRefusesATabThatHasLeftTheAllowlist…` pins that for each. **Action classes:** reads (read, find, screenshot, scroll, hover, resize, console, network) are ungated; click, click at a point, key and drag are the gated class; form_input and type set a value and are ungated. Network rows keep method, status and the address without its query, never headers or bodies. Console and network text is page-authored and goes to the model labelled untrusted. **`chrome_script` and `chrome_upload` are tools of their own**, so a standing grant for clicks cannot cover running script or sending a file. `chrome_script` is off unless `agent.main.chromeBridge.allowScript` is true; it is refused for any other agent at write time and ignored at read time, and when it is off the tool refuses without prompting, since there is nothing to approve. When it can run, every call is dangerous and `neverRunsUnasked`, and the click override does not exempt it. The address is checked before the script and again after, and a result from a page the script navigated away to is discarded. `chrome_upload` resolves its path through `FsPaths.resolveTargetPath` like every workspace tool, refuses persona files at the workspace root and anything over 25 MB, and is exempt from approval only for the main agent with the click override. The file path goes to the extension as an absolute path on the machine, so it does not work when JClaw runs in a container the browser is not in.
- **Recording is `ChromeRecorder`, with every size capped.** `record_start` and `record_stop` on `chrome_control`; a frame is a screenshot captured at most 800 px wide (WebP quality 60, or PNG for GIF) after navigate, click, type, form_input, key, drag and scroll. Caps: 30 frames by default and 100 at most, 25 MB held, 20 minutes unfinished, 4 recordings at once; each is a constant in the class. The JDK has no WebP reader or writer, so the browser encodes WebP and `AnimatedImages.webp` only joins stills into an animated WebP (a RIFF container); GIF needs pixels, so a GIF recording captures PNG and `AnimatedImages.gif` encodes them through ImageIO. `both` captures each frame twice. A frame from a page off the agent's allowlist is left out like a refused screenshot, and frames that differ in size from the first are left out. Output was checked against `webpmux`, Pillow and `ffmpeg`; `ffmpeg`'s WebP demuxer cannot read animated WebP, which is its limitation, not a defect in the file.
- **`read` and `find` describe a control by more than its visible text.** The extension returns a `hint` (its `<label>`, `aria-label`, `aria-labelledby`, placeholder, title, and for a form control its name and autocomplete) when that differs from the visible text, and the resolved input type, so a blank field reads `input[email]  (placeholder: Email; name: email)` and not a bare `input`. Without it, two empty inputs on a checkout page cannot be told apart by any reader. **`find` can ask a model.** Settings → Chrome → Finding elements names a model (`chromeBridge.find.provider` and `chromeBridge.find.model`); unset, `find` is the extension's word match and sends nothing anywhere. With a model, `find` reads the tab, sends the model the title, the request and the element list in one call, and shows the refs it names (at most three, each checked against the list, so a page cannot make it name an element that is not there). A provider that is not configured falls back to the word match quietly. A call that fails (no API key, the provider down, an unreadable reply) also falls back, but the answer then begins with a note that the find model did not answer, so the agent does not take a word match on a whole sentence for what it meant; a refusal for the site list carries no such note. The labels go to the model's provider, and to ollama.com for an Ollama cloud model. Measured 2026-11 on 22 to 23 questions over three real pages, one run each: DeepSeek 4.1 Flash on Ollama cloud picked the right element 21 times in one call of about 0.6 s and 1,800 tokens, with no JSON mode (the cloud route ignores `format`, so the reply is read as plain refs); the Ollama decision endpoint, which takes 2 to 26 candidates a question and so needs a tournament of about 5 calls, got 20 in about 3 s (cloud) and 13.6 s (local); the word match got 4. The decision models were confidently wrong on unlabeled inputs before the `hint` above and on look-alike controls after it; the one miss for DeepSeek was "get newsletters by email", where it chose the email box over the Subscribe button.
- **The tool is opt-in for every agent, `main` included, and offered only on turns the owner reads alone** (`OPT_IN_FOR_EVERY_AGENT` and `OPERATOR_TURN_ONLY` in `ToolRegistry`). Page text goes to the model labelled untrusted; that is a nudge, not a defence against prompt injection.
- **The pairing token is a separate credential from `ApiToken`** and is stored as a hash. It travels in the first `hello` frame, never the URL, and the socket closes at 5 s if none arrives. The socket checks that `Origin` starts with `chrome-extension://`, which a web page cannot forge.
- **One extension at a time.** A second connection replaces the first and fails what was waiting on it. A request waits on an untimed `get()` while a `RetryScheduler` task supplies the deadline, because a timed park on many virtual threads is JDK-8373224.
- **Tests that attach a fake extension hold `ChromeBridgeSync`**, since the connection is a process-global. `ChromeBridgeSocketTest` is the only test that opens a real WebSocket to the app.
- **Not built:** screenshots through the tool (the extension supports them), and a check that the extension's id matches the one that paired.
