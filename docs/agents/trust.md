# Trust — who may do what

Read this before touching an `/api` action's `@AgentAccess`, `RequestPrincipal`, `DangerousActionGate`, inbound handling in `app/channels/`, tool-approval grants, persona files, or a URL, host or path that a model or a page supplies.

## The agent principal

- JClaw has two trust axes. **The agent principal:** an unscoped `findById` on an `OPERATOR_ONLY` route is not IDOR, and neither is one on an `OPEN` route whose body admits only the operator and `main`. `/api/providers`, the config reads and the channel list answer `main`, so a leak there is still fixed at the seam (`SsrfGuard`, `ConfigService.maskValue`, the dangerous-verb gate): the route refusing other agents does not mask what `main` reads.
- Every routed `/api` action declares `@AgentAccess`: `OPEN`, `OWN_ONLY` or `OPERATOR_ONLY`; no annotation means `OPERATOR_ONLY`. Every auth interceptor calls `AgentAccessGate.enforce()`, which refuses the agent principal before an `OPERATOR_ONLY` action runs, and `JClawApiTool` advertises and calls only the other two levels — so put no operator guard in an `OPERATOR_ONLY` body, and never reintroduce `@ChatHidden`, `@AgentCallable`, `PATH_BLOCKLIST` or a hidden-but-reachable route: a route an agent should see is `OPEN`, otherwise it is refused.
- A mutating `OPEN`/`OWN_ONLY` action names what bounds it in a non-blank `reason`, and an `OWN_ONLY` action reaches `RequestPrincipal.mayReachAgentScopedRow` (a row route 403s) or `callingAgent` (a list route pins its query to the caller); `CapabilityRulesTest.everyRoutedApiActionDeclaresAnAgentAccessLevel` fails the build otherwise. Widening what an agent can invoke means editing the pinned list in `JClawApiToolTest.theCallableApiSurfaceIsExactlyTheseRoutes`.
- A `GET` route's `@ApiResponse` type carries no credential-named `String` — expose a `hasX` boolean, as the channel binding views do. Give a new `GET` a declared response type rather than adding it to `CredentialReadGateConformanceTest.UNCHECKABLE_GET_ROUTES`, and delete a line from that list once its route declares one.
- Read the calling agent from `RequestPrincipal.callingAgent()` and its turn's origin from `callerOrigin()`, never from a request field: `JClawApiTool` stamps `X-JClaw-Agent-Id` from the `Agent` it is handed and `X-JClaw-Caller-Origin` from `DangerousActionGate.effectiveOrigin`, never from the model's arguments, and both count only on an agent-originated request. An unstamped bearer is an unidentified agent, which `OWN_ONLY` refuses.
- `POST`/`PATCH /api/tasks` only record or lower a task's fire-time origin to the caller's; only the operator's `POST /api/tasks/{id}/trust` raises it.
- The operator and `main` reach every row (`isOperatorOrMainAgent`); any other agent reaches only its own conversations with their messages and attachments, tasks with their runs, run transcripts and transcript-search hits (by the task's `agent`, JF-284), its own settings, to read (its row, prompt text and breakdown, effective shell allowlist, tools, skills and their files, memory-migration status and WhatsApp bindings, JF-285), subagent runs (by `parentAgent`), scrape jobs (by `agent`), the processes in its own workspace, and (JF-292) the prompts it owns (`Prompt.ownerAgent`: the creator picks the owner, JF-307, and only the operator and `main` change it afterwards, with `ownerAgentId` on the update, JF-308; a prompt with no owner is the operator's, which a deleted agent's prompts become), its notifications, to list and acknowledge, its video-generation jobs (by `agent`, else the conversation's agent), a hosted app's file from its own conversation, and its own cost, latency and compression rows — `main` sees down the tree, nothing sees up or across. A row route refuses another agent's row with `mayReachAgentScopedRow`; a list, a count or a search pins to the caller with `RequestPrincipal.scopedAgentId` before the query runs and before any limit, and a by-id list leaves another agent's id out as it does an unknown one. A web delivery keeps to the same line (JF-289): the `message` tool's `channel=web` and a task's `web:<id>` reach only the agent's own conversations and its parent chain's (the conversation that started a run it is the child of, and every conversation above that), and `main`'s reach any. `services.WebDeliveryScope` decides it when a task is saved and again when the message is sent, and answers a conversation out of reach exactly as it does a missing one. A task records who saved its delivery (`Task.deliverySetByOperator`, JF-305, read-only in the task's JSON): the operator and `main` save any conversation for any agent's task, and the fire delivers there, while a target the agent saved, and a row from before the column, is judged as the agent's at the save and at the fire. `Task.setDelivery` is the only writer of the delivery (`WebDeliveryScopeTest` fails an assignment of the field alone), and an agent's save of a delivery through `task_manager` or the API makes the target the agent's again, the operator's own target sent back included, so an agent never carries the operator's reach onto a target it chose. The reach is lent to the task as it stood, so an agent's change of what a fire produces or when it fires (the description, the name, the schedule, the timezone, the payload type, the tool list or the model) makes the saved target the agent's too, until the operator or `main` saves it again (`Task.agentChangedTheFire`, called by `PATCH /api/tasks/{id}` and `task_manager`'s `updateTask`): otherwise an agent could rewrite a task the operator pointed at another agent's conversation and have its own text delivered there. `paused` and `autoDeleteOnComplete` switch the task on or off as it stands and leave the record alone, as do the pause, resume, run and retry routes, and an edit by the operator or `main` keeps it.
- A route that serves the instance and not one agent's rows answers only the operator and `main` (JF-292): it stays `OPEN` with a `reason` that says so, and its body refuses first with `RequestPrincipal.requireOperatorOrMain`, which answers 403 `agent_scope` naming `main`. That covers the instance's setup (the MCP servers, the config rows and logging levels, the channel configurations, the providers and their models, the model router's status and usage, the coding-harness commands, and the guided tour's step counter, which decides whether the operator's dashboard opens the tour, JF-293), the host and its lifecycle (the live latency histograms, the pool, JVM and log metrics, the circuit breakers, the workspace size, the restart, upgrade and Java-runtime status), and the routes that dial out or spend (prompt generation and export, a provider probe or model discovery, the price refresh, the MCP server test, a printer's options). What stays open to every agent is a catalog or a capability check with the same answer for all of them: the skill, slash-command, prompt-category and timezone lists, the hosted apps, `/api/status`, the guided tour's status, the media, OCR and printer state its own tools depend on, and the active channel kinds. The tool catalog is open too, and differs by caller in one way (JF-293): an agent other than `main` is shown an MCP server's handle and actions only when it may call that server (`ApiToolsController.mcpServersShownTo`, reading `McpServerCatalog.serversForAgent`), because a handle names a service the operator connected. That holds on `GET /api/tools`, `/api/tools/meta`, `/api/tools/{name}` and the agent's own `GET /api/agents/{id}/tools`; a server it may not call reads by name exactly as an unknown tool does, and an agent-originated request that names no agent is shown no server. A new route that reads setup or another agent's activity takes one of the two shapes above, never a bare `OPEN`.
- Bound a dangerous argument or field instead of closing its route: `services.printing.PrintTargetGuard` keeps `host`/`port` open but refuses link-local, multicast and `0.0.0.0` (for the printer tool and, since JF-294, for `GET /api/printers/options`, which exempts only the saved default printer; the host is judged as the IPP URL reads it, so a path, query, userinfo or percent-escape in the string does not hide it), and makes `PrinterTool.dangerous(args)` true for an address that is neither a discovered printer nor the saved default; MCP reads, writes and the test answer only the operator and `main` (JF-285, JF-292: a custom agent never adds a server, and with it tools, to itself), and `requireMainForStdio` still limits a `STDIO` transport — an unsandboxed `ProcessBuilder` outside the shell allowlist — to the operator and `main`, checked against the row's effective transport on update; an update that moves an HTTP server to another scheme, host or port drops its saved headers unless the same request sends their values, and refuses a saved header's mask sent with the new address (`McpServerService.sameOrigin`, JF-291), and a redirect to another scheme, host or port is followed without them (`HttpFactories.keepingToOrigin`, JF-304; a 401 or 403 answered there fails the connection with an error that names the redirect), so a saved secret is never sent to an address it was not entered for; `requireOperatorForAcpChange` refuses an agent flipping `acpAllowed`; `PUT /api/router/models/{taskClass}` is `OPEN` but answers only the operator and `main`, writing the five `router.<class>.models` keys alone, while every other router key stays on the operator-only `POST /api/config`; `POST /api/providers/{name}/models` answers only the operator and `main` too, because every model picker lists a provider's models (a list `ConfigService.setWithSideEffects` refuses is a 400 with the reason, JF-294), and so do `POST /api/agents` and `PUT /api/agents/{id}`, a custom agent's own row included (JF-285: no agent reconfigures itself), where a model `main` picks must be registered, since an unregistered one would switch that agent off. The model and thinking level a custom agent runs on are `main`'s and the operator's to choose everywhere else too (JF-286): a conversation's model and thinking overrides, a task's `modelProvider`/`modelId` through the API or `task_manager`, and `subagent_spawn`'s model arguments.
- `jclaw_api` is opt-in for every agent but `main` (JF-293, which replaced JF-287's `main`-only rule once the scoping above was in place): it sits on `ToolRegistry.OPT_IN_FOR_NON_MAIN_AGENTS` beside `exec` and `agent_spawn`, off until the operator switches it on with `PUT /api/agents/{id}/tools/jclaw_api`. That route is `OPERATOR_ONLY`, so no agent grants it, to itself or to another, `main` included. A subagent never has it, whatever it or its parent was granted (`ToolRegistry.computeDisabledTools`): the grant is the operator's to one agent, and a copy is made by that agent's spawn. `__evaltest__` never has it, whatever grant row or eval suite names it, and nor does an unsaved agent other than `main`. A row saved before JF-287 made the tool `main`'s alone counts as that switch: nothing removes it, so an agent the operator gave the tool then has it again, within the scoping above. A granted agent is offered it only where the owner reads the reply alone, as `main` is, and the grant widens nothing a route decides: every request the tool sends is stamped with the calling agent, so that agent reaches its own rows and is refused another agent's and every route that is the operator's and `main`'s (`JclawApiGrantedAgentScopeTest` drives the three through the tool).
- `jclaw_api` gates the parsed `HttpUrl.encodedPath()`, never the model's string, and refuses `#`, a backslash, `//` and dot-segments before parsing; keep both, or `..` (or `%2e%2e`) resolves past the gate and out of `/api/` into the `{controller}/{action}` catch-all. `describeCall` labels a call from the same plan `execute` sends, so an approval prompt names the resolved endpoint, never the model's string.
- A skills route takes one folder name, never a path: `WorkspacePathGuard.resolveChild` gives null for anything else and the route answers 400 (JF-291). `resolveContained` also accepts the root and any depth below it, and a name such as `skill/credentials` would then put a credential file outside the `credentials/` folder the mask is judged by. The on/off switch judges the name's spelling alone (`isOneSegment`), because `SkillLoader` follows a skill folder that is a link out of the skills folder and the switch is the operator's control over it.
- `serveWorkspaceFile` and `ApiAttachmentsController.download` send `Content-Security-Policy: sandbox` always, and `attachment` unless it is a raster image (never SVG, `utils.ServedFiles`) or audio, or a PDF on the workspace route — there is no global CSP, so a route serving agent-written bytes inline carries its own.

## The channel sender

- **The channel sender** is the other trust axis, independent of the agent principal: a turn is owner-initiated only when its sender id equals the binding owner's — Telegram, and Slack once `ownerUserId` is set, DM or group alike. A non-owner group member, every WhatsApp sender and every user of an owner-less Slack binding are guests. `DangerousActionGate.withOwnerInitiated` binds it in `TelegramInboundTurn` (webhook and poller), `TelegramReactionNotifier.handleReaction`, `SlackInbound`, `ScrapeJobService`'s and `TaskRunReports`' completion turns (which re-bind the value captured at submit) and `QueueDrainOrchestrator.runOwned` (which re-binds the value each `QueuedMessage` recorded at enqueue, and a guest's for a batch holding one); `ownerInitiated()` reads it, and unbound means guest — never default it to true. Web chat and voice mode are the operator's origins (`ChannelOriginTrust`). A hosted app (`app`) needs the signed-in session as they do, but its bundle writes the message text, so it is not one.
- A standing tool-approval grant is spendable only on an owner-initiated turn or one whose effective origin classifies as `OPERATOR` — its key `(agentId, toolName)` carries no channel, and no action either: one grant on `jclaw_api` covers every write it can make, so the per-action record is the line `JClawApiTool` writes for every call in the `jclaw_api` category (method, path, the body's field names and never its values, the outcome) and the call `Tool.describeCall` names in the gate's prompt and log lines. `jclaw_api` and `agent_spawn` (which hands the turn's task to another operator agent with no tool comparison) take the narrower `DangerousActionGate.ownerReadsAlone` (an operator turn outside a group chat; a fire passes by `AgentRunner.fireOffersOwnerTools`): failing it, the tool is neither offered (`ToolRegistry.turnDisabled` and `forTurn` at every prompt and tool-list site) nor callable, and `ParallelToolExecutor` refuses a tool the turn was not offered before the gate, so no such call asks the owner. `Commands.execute(…, ownerInitiated)` refuses `/subagent`, `/prompt` and the `/model` write forms to a guest (they reach every subagent run, the operator's prompt library and the conversation's model); every other command stays open, and web chat passes `true` because it sits behind `AuthCheck`. A Slack binding with no `ownerUserId` refuses those commands to everyone, the operator included — configure the owner rather than file a bug. `/subagent info|log|kill` is deliberately not scoped to the calling agent's runs: one operator owns every agent.
- `TelegramReactionNotifier.reactorAllowed` drops a private-chat reaction whose `reactorId` is not the owner: a DM peer id resolves to the owner's conversation and the default `own` policy admits every DM reaction, so a stranger's reaction would otherwise run a turn over the owner's history and receive the reply. Group reactions keep `shouldNotifyReaction`. Label reaction text `[reaction]`, never `[system]` — the reactor chooses their own display name.
- `DangerousActionGate.hasStandingGrant` ORs a never-pruned in-process set with the `tool_approval_grant` table, so deleting the row alone fails open: pair every `ToolApprovalGrant.revoke` with `DangerousActionGate.revokeGrant`, and an agent delete (its rows go by `ON DELETE CASCADE`) with `revokeGrantsForAgent`. The row's granting channel and peer are provenance only; the gate never reads them. Escape approval prompts per grammar: Telegram `escapeHtml` (`& < >`); Slack `SlackMarkdownFormatter.escape` plus a zero-width space after each backtick, or a model-controlled argument closes the code fence and renders the rest of the prompt as mrkdwn. Leave `*` and `_` unescaped — Slack has no escape for them, and the block structure is what matters. A prompt shows a call's arguments whole (JF-294): `DangerousActionGate.Prompt` cuts the raw text and escapes each piece after the cut, so no piece ends inside an escape or a surrogate pair, and sends as many messages as it takes, each inside its channel's limit (`TelegramApprovalService.MESSAGE_MAX_CHARS` 4096, `SlackApprovalService.SECTION_MAX_CHARS` 3000, both from the channels' documentation, not measured), with the buttons on the last. Each part's label names its part and its call (`Arguments, part 2 of 3, call 3fa9c1:`; the tag is the first six hex characters of SHA-256 over the tool's name, a newline and the raw arguments). The services send one prompt at a time per chat under `ApprovalRegistry.sending`, a striped lock keyed by bot token and chat (Slack: token, channel and thread): never send a prompt's messages outside it, and never hold it across the wait for the tap. Arguments over 12,000 characters, or prompt lines over 2,000, are refused unasked and the model is told the length and the limit. A part that fails to send resolves `EXPIRED`: never add a retry that could put buttons under a partly shown prompt. The Why line is the model's text outside the block, so it is one line, capped at 300 characters, and on Slack sits in a code span.

## Persona files

- A persona file (`SOUL.md`, `IDENTITY.md`, `USER.md`, `BOOTSTRAP.md`, `AGENT.md`) reaches the prompt only at its approved version (`services.PersonaFileApprovals`, JF-136). `WorkspaceFiles.writeWorkspaceFile` is JClaw's own write and approves one; a tool writing for the agent, a download or a scrape, uses `writeAgentFile`, which approves nothing, so a persona file it lands on waits for the operator. A JClaw edit to existing text goes through `applySystemEdit`, which edits the approved and the on-disk text apart, so an agent's pending change is never approved with it. A new tool that brings no outside text into the conversation overrides `Tool.readsOutsideContent`: the default `true` keeps every later persona edit in that conversation waiting for the operator, as a prompt that carried a memory resting on someone else's words does. The filesystem tool approves only the text its write made, and an append or edit only on top of the approved version.

## Destinations and URLs

- A model-chosen destination whose legitimate targets are loopback or the LAN (a printer `host`, a provider or MCP URL) is screened with `SsrfGuard.isBlockedForProvider`, never `isUnsafe`, which also blocks loopback and RFC-1918; a web URL the model browses, fetches or scrapes stays on the strict `assertUrlSafe`/`SAFE_DNS`. A failure string from `PrintDispatcher.print` never carries the transport exception — "refused" versus "timed out" is a port scan — so it returns `<protocol>: no response` and keeps the detail on `EventLogger.warn`; `status` and `cancel` still surface it through `PrinterTool.execute`.
- Parse a URL the page supplies (a `Location`, a harvested href, a sitemap entry, the browser's final URL) with `utils.Urls`, which percent-encodes what `URI` rejects and browsers send raw after the authority; keep a URL an operator or the model typed on `URI.create`, so a typo fails at the edge with a message naming it. `SsrfGuard`'s strict path parses with `Urls`, so the guard reads the host the fetcher sends; `assertProviderUrlSafe` stays on `URI.create`, because `LlmProvider.buildUri` parses the saved base URL that way on every turn.
