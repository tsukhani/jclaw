# The context pipeline

Read this before touching `CompressionPipeline`, `CompactionGate`, `ContextWindowManager`, `ContentTypeDetector`, `ToolResultPruner`, a media rewrite, or a tool's `verbatimResult` or `keepsResultInContext`.

- A media bearer addresses its message by position (`chatMessageIndex`), and `CompactionGate` (rebuilds the list from the persisted rows) and `ContextWindowManager`'s drop-oldest branch (shifts every survivor down) replace the list under it: apply a media rewrite after both, through their `MessageHydrator.Hydration`-taking overloads, which return bearers matching the list each produced — never before compaction, which discards anything written earlier. Pruning, compression, tool-result truncation and `CurrentTimeInjector` are index-preserving. `VisionAudioAssembler.holdsUserTurn` skips a slot that is out of range or not `USER`, so a missed re-base skips the rewrite rather than throwing.
- A compaction reports its progress through `services.CompactionProgress.SINK`, a `ScopedValue` the transport binds around the turn's prologue (`StreamingAgentRunner`) or around `/compact` (the web controller reads the answer's `compaction` field, a channel dispatcher binds it itself); `SessionCompactor` reads it unannounced, so a compaction run on another thread than the binder's reports nothing, and a `start` frame goes out only once a cut exists, so a conversation with none flashes no card each turn. The web chat handles these frames before it has a bubble, because they precede the turn's `init`.
- Automatic compaction stays off the turn's path (JF-367). `CompactionGate.afterReply` measures the next turn's request once a reply comes within `SessionCompactor.BACKGROUND_MARGIN_PERCENT` of the trigger and compacts it on a virtual thread, and a turn past the trigger whose request the window still takes is sent uncompacted beside a compaction of its own request; only a request the window does not take compacts inline. A conversation runs one compaction at a time through the gate's in-flight map: a background start skips a running one, the inline path joins it, and `/compact` waits for it through `CompactionGate.runExclusive`. A new caller of `SessionCompactor.compact` goes through `runExclusive` as well: two compactions from one floor plan the same rows and store a segment each.
- `ContentTypeDetector.isCode` routes to `CODE` only when `CodeCompressor.detectLanguage` (which returns on the first hint that matches) finds a language and there are two hint-carrying lines, or at most five non-blank lines in total; `JS_HINT` still answers JAVASCRIPT for any line beginning `export `, so the signal count, not the hint, keeps prose out of `CODE`. The C# hints (`CSHARP_USING`, `CSHARP_NAMESPACE`) count toward no signal: they only keep C#'s `public class` from JavaParser, so a `using` line never makes content `CODE`. A Markdown document, two fence lines or `##` headings indented at most three spaces, is never `CODE`: the regex path keeps declarations, which leaves a document only its code. Bias toward TEXT: misrouting code costs compression quality, misrouting prose costs the content. Pin JavaParser at `BLEEDING_EDGE`, not its `JAVA_11` default, so a dependency bump cannot leave the parser a release behind; share the `ParserConfiguration` and build a `JavaParser` per call — the instance is not thread-safe, the configuration is.
- `AgentPromptPreparer.prunedAndCompressed` seeds the tool loop's list, so `CompressionPipeline` and `ToolResultPruner` meet their own output on later rounds. A `ccr_retrieve` handle is a hash of a durable `Message` row and a hash of compressed text matches none, so compression records each String it writes with its original's handle: a recorded String passes through, and a stub names the recorded handle (`CompressionPipeline.retrievalHandle`). Never decide this from the marker: a tool result is outside text and can end in a copy of it. The record is by instance, so a copied `ChatMessage` keeps it and a step that rebuilds the text does not: `ContextWindowManager.truncateToolResultContent` passes it on with `carryHandle`, and a new rewrite of tool text must too.
- `CompressionPipeline` runs before every model round, so it sees a tool result before the model does. It leaves an unread result whole (one that follows the last assistant message, up to `chat.compression.firstViewMaxTokens`) and compresses it from the next round on: compressed unread, 30% of large results were fetched back through `ccr_retrieve` in the same turn, 86% for `exec` (measured 2026-10-13 over 45 days), each costing a round and a second full copy; under the rule, 15% for `exec` (2026-10-14 to 10-18). A result the model picks from across rounds declares `Tool.verbatimResult(args)` and is never compressed, since the JSON compressor keeps three entries of a list: `McpServerTool`'s action list, `describe` and resource `read`, and `jclaw_api`'s `discover`. A new catalog-style call declares it too, and caps its size, as `read` does at `READ_MAX_CHARS`: a verbatim result escapes the first-view bound, and `ContextWindowManager`'s tool-result truncation spares the most recent messages (`chat.truncateToolResultsPreserveRecent`, default 4). A large MCP server lists names and one-line summaries (`FULL_CATALOG_MAX_CHARS`), and `{"describe": [...]}` returns the schemas of chosen actions; never return every schema of a large server in one result. Separately, `ToolResultPruner` stubs any large result from an earlier turn whatever an agent's compression setting; a result the model keeps following for the whole conversation (a skill's SKILL.md, through `skill_read` or a `filesystem` read) declares `Tool.keepsResultInContext(args)`, is never compressed, and is kept as Claude Code keeps skills: newest first, each up to `SKILL_KEEP_CHARS` (20,000) within `SKILL_BUDGET_CHARS` (100,000) a conversation, an older copy of the same text stubbed. A SKILL.md therefore stays under 20,000 characters, detail in `references/`; the filesystem tool warns on a save past it.
