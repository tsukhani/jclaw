# Release signing

Read this before touching `bin/sign-release.sh`, `utils.ReleaseSignature`, `install.sh`, `install.ps1`, `jclaw.sh upgrade`, `docker-pull-verified.sh` or the Jenkins Release stage.

- Releases are signed: the Jenkins Release stage runs `bin/sign-release.sh` with the `jclaw-release-signing-key` credential (ECDSA P-256) and attaches `SHA256SUMS.sig`. `jclaw.sh upgrade` pins the public half and refuses any release above 0.19.25 that does not verify, the asset-URL override being the one deliberate bypass. The upgrader verifies with `utils.ReleaseSignature`, run out of process on the install's `precompiled/classes.jar` alone, so keep that class on the JDK (`ReleaseSignatureTest.theVerifierStandsAlone`). The installers carry no key: a first install has no earlier key to anchor to, and `install.sh` would fetch its key from the same release as the bundle, so a signature check there would stop nothing a swapped release could not also swap. `install.sh` therefore checks the bundle's SHA-256 against the unsigned `SHA256SUMS` (a corrupt or truncated download, not a swapped release); a missing manifest or hasher warns, a differing hash refuses. `install.ps1` checks nothing and warns. The bundle `install.sh` fetches holds the key every later upgrade pins, so the first install's trust is TLS plus GitHub, as for other `curl | sh` installers. The same stage signs `IMAGE_DIGEST`, the digest buildx reports for the image it pushed, since a tag can be repointed and a digest cannot; nothing enforces it: a Docker user runs `docker-pull-verified.sh`, which refuses a missing or wrong signature, only warns where there is no `openssl`, and pins `JCLAW_IMAGE` in `.env`, or checks by hand against `release-signing.pub` (INSTALL.md). The cleanup stage deletes only images no listed Release needs (`bin/ghcr-prune.mjs`), so every listed `IMAGE_DIGEST` stays pullable: never prune by a count of package versions, because one multi-arch image is three of them. `ReleaseSigningConformanceTest` holds all three copies of the key equal and tied to the credential. Every command that fetches an installer or `release-signing.pub` uses `releases/latest/download/`, never a branch on `raw.githubusercontent.com`: pull requests merge on GitHub's `main` before any test or release, and the installers are the entry point, so a merged change would reach new installs at once. The Release stage attaches the tagged commit's copies and lists them in `SHA256SUMS`.
- Jenkins runs Sonar and coverage but never lint, typecheck or e2e; its release notes are the commit body only when the subject is exactly `Release vX.Y.Z`, which `/deploy` writes. `/deploy` pushes the version's signed tag only once that commit's build has passed, and a RELEASE build waits up to 20 minutes in Setup for that tag to reach GitHub, then refuses; `gh release create --verify-tag` also refuses a version without one. A RELEASE build skips Test and Sonar when the last successful build's description is `tested <its commit>`, which every green build writes.
