# Release signing

Read this before touching `bin/sign-release.sh`, `utils.ReleaseSignature`, `install.sh`, `install.ps1`, `jclaw.sh upgrade`, `docker-pull-verified.sh` or the Jenkins Release stage.

- Releases are signed: the Jenkins Release stage runs `bin/sign-release.sh` with the `jclaw-release-signing-key` credential (ECDSA P-256) and attaches `SHA256SUMS.sig`. `jclaw.sh upgrade` and `install.sh` each pin the public half and refuse any release above 0.19.25 that does not verify, the asset-URL overrides being the one deliberate bypass. The upgrader verifies with `utils.ReleaseSignature`, run out of process on the install's `precompiled/classes.jar` alone, so keep that class on the JDK (`ReleaseSignatureTest.theVerifierStandsAlone`); the installer has no trusted class yet and uses `openssl`. Only a missing or wrong signature refuses: a machine without `openssl` is warned and installs unverified, because that is the operator's machine and not something a swapped release controls. `install.ps1` cannot verify at all and warns the same way. The same stage signs `IMAGE_DIGEST`, the digest buildx reports for the image it pushed, since a tag can be repointed and a digest cannot; nothing enforces it: a Docker user runs `docker-pull-verified.sh`, which refuses a missing or wrong signature, only warns where there is no `openssl` as the installer does, and pins `JCLAW_IMAGE` in `.env`, or checks by hand against `release-signing.pub` (INSTALL.md). The cleanup stage deletes only images no listed Release needs (`bin/ghcr-prune.mjs`), so every listed `IMAGE_DIGEST` stays pullable: never prune by a count of package versions, because one multi-arch image is three of them. `ReleaseSigningConformanceTest` holds all four copies of the key equal and tied to the credential.
- Jenkins runs Sonar and coverage but never lint, typecheck or e2e; its release notes are the commit body only when the subject is exactly `Release vX.Y.Z`, which `/deploy` writes. `/deploy` pushes the version's signed tag only once that commit's build has passed, and a RELEASE build waits up to 20 minutes in Setup for that tag to reach GitHub, then refuses; `gh release create --verify-tag` also refuses a version without one. A RELEASE build skips Test and Sonar when the last successful build's description is `tested <its commit>`, which every green build writes.
