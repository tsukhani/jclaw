# Subagents and coding runs

Read this before touching `SubagentRun`, `SubagentRegistry`, `subagent_spawn`, `agent_spawn`, `AgentRunner.taskFireParent`, a task's model pin, coding runs or `AgentService.delete`.

- A subagent run has at most one parent: the conversation that started it, or the task run when a task fire did (`SubagentRun.parentTaskRun`), never both, and neither for an eval capture's run. `ToolContext.noParentChat()` means the turn has no parent chat (every `AgentRunner.runForTask` turn, fire or capture), so never resolve one by recency there; `DeliveryResolver.operatingConversation` returns empty under it, where it would otherwise fall back to the agent's latest conversation, which filed task-started runs under an unrelated chat and ran a capture's inline child inside one (JF-158). Gate on `noParentChat()`, not on `taskRunId()`, which a capture leaves null. A fetch join on a run's parents is `LEFT`; `codingrun.step` names a `conversationId` only for a chat-started run, and the chat adopts a run by that id alone.
- A fire-started child takes the fire's origin as its channel (`SubagentChildBootstrap.taskFireChannel`, so `DangerousActionGate` judges it as it judges the fire) and reads the rest off `AgentRunner.taskFireParent`: the task's pin as its model (an `agent_spawn` callee always runs on its own model: `ownModel` in `SubagentChildBootstrap.resolveChildConversation`), and the task's tool list in `Conversation.enabledToolNames`, which every descendant copies. A new place that builds a conversation turn's `ToolDef`s applies `TaskToolPolicy.restrictSubagent` and `ToolRegistry.forTurn`, as `AgentPromptPreparer.turnTools` does, or a fenced task leaves its fence by delegating. The prompt follows the same list: each place that assembles one for a fire or a conversation turn passes `ToolRegistry.turnDisabled` (the fire, both `AgentPromptPreparer` paths, `CompactionGate`'s rebuild and `nextTurnRequest`), or its catalogs name tools the turn cannot call. Skills are deliberately not filtered by a list, except that one declaring only `jclaw_api` drops out when the turn withholds it: a task may use part of a skill whose declared tools reach past it. A single spawn's `mode=inline` runs as `session` in a fire, with a `note` in the result, rather than being refused: an error costs an unattended run a round, though a `tasks[]` batch refuses it, as in chat; `context=inherit` grants the tool union without a summary.
- A task run owns the runs it started: `SubagentRegistry.deleteRunsStartedBy` removes them, stopping any in flight, before the task runs go. The database cannot (a run's transcript, Lucene docs and spawned agent are outside any FK), and without it the 10-run cap and retention prune task history while the runs pile up. `ON DELETE SET NULL` on `parent_task_run_id` is only the net for a run that starts mid-delete.
- A run's child agent is not always the run's: an `agent_spawn` hand-off runs on an operator's agent, which keeps `parentAgent == null`, so its own subagents count depth from 0 and `subagent.maxDepth` never refuses a hand-off. `subagent.maxHandOffs` bounds a hand-off tree instead: its counter rides `RunScope.handOffs` down the tree and sits on the turn's `LatencyTrace` at the top. A subagent never has `agent_spawn` (`ToolRegistry.computeDisabledTools`). Delete an agent with a run only when the spawn created it (`childAgent.parentAgent != null`), and never delete an inline run's `childConversation`, which is the parent chat. `SubagentRegistry.deleteRun` and `ConversationDeletionCascade` are the two that decide; deleting such a run or its chat used to delete the operator's agent, workspace and memories with it.
- `AgentService.delete` runs `em.clear()` partway through (`AgentDeletionCascade.delete`): every entity loaded before it is detached, so re-read by id before `entity.delete()` and load rows inside the loop. `SubagentRegistry.deleteRun` takes an id for this reason.
- A coding run is `SubagentRun.runtime = 'acp'`, set at the insert. `workdir` is set later and stays null for a run refused approval or a folder, so it does not identify one. `resolveAcpWorkdir` throws rather than return no folder: a harness writes outside JClaw's tool confinement, and the server's own directory is the checkout on a source install. `CodingRunMonitor` learns that a run ended only from the live `codingrun.done`, so a view that mounts it afterwards passes `recordedStatus`.
- A task with both `Task.modelProvider` and `Task.modelId` set fires on that model (`AgentRunner.runForTask` applies it as the stub conversation's override); an unpinned task, or one pinning an unconfigured provider, follows its agent's current model.
