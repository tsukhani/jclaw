## jclaw

AI agent platform on a Play 1.x fork (Java 25, virtual threads) with a Nuxt 4 SPA and seven Python sidecars the JVM spawns. Single-operator by design: one admin, no user entity; the UI, the user guide and the tests that pin that text call the product JClaw Pro, and everything else — Java, comments, this file — says single-operator, never an edition name. Tickets are Jira JCLAW; planning lives in `_bmad-output/`; every rule below has its reasons in the sections that follow this block. Terms: a *turn* is one agent invocation, many messages and tool rounds; a *channel* is the origin (web, slack, telegram, whatsapp, voice, app), not a component; a *binding* attaches a channel to an agent; a *harness* is an external ACP coding agent, not this CLI; *Standing Orders* are the workspace files `SystemPromptAssembler` injects.

## Policy

- Never `git push` a commit: `/deploy` is the only push, run from the main checkout on `main`, never a worktree; `/renovate` deleting its merged `renovate/*` branches is the one other sanctioned push. Never `--no-verify`, never force. Stop at the local commit and report the hash.
- Never run a `./jclaw.sh` subcommand that stops the instance (`restart`, `stop`, `restore`, `repair`, `compact`, `reset`, `upgrade`, `uninstall`), or kill the server PID, without asking — the instance may be serving live work; a task that mentions a restart is not the approval.
- Never hand-edit the seven upstream-imported skills (`skills/{claude-designer,powerpoint-pptx,humanizer,youtube-transcript,git,frontend-design,ffmpeg-video-processing}`) — a re-import overwrites them; the other skills under `skills/` are local and edited normally. `docs/architecture/` is a snapshot nothing regenerates: correct a wrong fact in place, never expand or restructure it.
- Commit messages and tags are public on the GitHub mirror: no credentials, customer specifics, or unreleased plans.
- Don't create worktrees or branches unless asked; work on `main`. One exception: when a test run here fails twice from another session's work, for a cause you can name (its mid-run edit reloading Play's classes, its test stopping the server), rerun it in a temporary detached worktree outside the checkout (`git worktree add --detach`, which seeds its own `PLAY_TEST_PORT`) holding `HEAD` plus only your diff, then remove the worktree; you still commit on `main`. Other sessions share this checkout: stage only your own hunks, never `git stash -u`. `/deploy` stages everything (`git add -A`), so check `git status` for other sessions' work before running it.
- The `jclaw_api` token exists only in the running process and the database keeps only its hash, so a restart mints a new one and there is no plaintext to SELECT. Read-only SELECTs on the live H2 (empty credentials, `AUTO_SERVER`) are fine. Third-party credentials cannot be hashed, so they are stored AES-GCM-encrypted (`enc:v1:`) under a key HKDF derives from `PLAY_SECRET` in `certs/.env` (`utils.CredentialCipher`, JCLAW-1455): the Config keys `ConfigService.encryptsAtRest` flags (`provider.*`, `search.*`, `scanner.*`, `*.hfToken`, `web_scrape.proxy.password`, `otel.exporter.secretHeaders`, `decision.jev.apiKey`, `decision.laya.apiKey`, `decision.baseten.apiKey`), the Slack, Telegram and WhatsApp binding token columns, and the secret values in `McpServer` and `ChannelConfig` JSON. A SELECT returns ciphertext, but `certs/.env` opens it, and a data file not yet compacted (`jclaw.sh compact`) or a backup Settings marks Unencrypted still holds plaintext: never copy a value read from any of them into output, commits or tickets.

## Where things are

- Rules with their reasons: the sections below, and the topic guides in `docs/agents/` they link. Settled verdicts before re-proposing work: `docs/spikes/` — gitignored, so it holds only what this clone wrote; earlier verdicts are in git history (`git log -- docs/spikes`; the last tracked set is `git show f93376c5^:docs/spikes/`).
- Every kind of documentation, comments and Javadoc included, is cataloged in `docs/README.md`: what each must agree with, how a docs sweep treats it, and the gates an edit inside a source file runs.
- Config validation lives in `ConfigService.setWithSideEffects` (a non-null return is the 403; `deleteWithSideEffects` refuses no delete); `POST /api/config` writes any non-reserved key, so "not in the UI" is no reason to skip it. Never seed a key another selection already implies.
- The fixed-name agents `main`, `__loadtest__`, `__loadtest_tools__` and `__evaltest__` are provisioned by code — never seed or delete them in tests.
- The AFK factory (`.sandcastle/README.md`) works Jira stories labelled `afk`, or in an epic labelled `afk`, unattended and returns each as a local `agent/<KEY>` branch for review; a story or epic labelled `afk-merge` it also merges, signed, into the checkout's `main` and moves to Done, never pushing. Everything else it writes lives in `~/.jclaw-factory`, never in the checkout.
- One implementation each, so a fix lands once: `jobs.RetentionDays` (all four cleanup windows), `AttachmentService.toView`/`toViews` (attachment JSON on the SSE frame and the REST read alike), `channels.TelegramInboundTurn` (the webhook and the poller run one turn), `SubagentSpawnArgs.batchChild`, `LocalSidecarDaemon.singleFlight` (every sidecar manager goes through it), `SubagentRegistry.deleteRun` (the single and the bulk run delete), `SubagentRegistry.deleteRunsStartedBy` (in front of every bulk delete of `TaskRun`; `TaskRunDeletionConformanceTest` fails a site that skips it), and `ConfigService.isDispatcherCapKey` on both the set and the delete arm. Grepping `app/` for `Mirrors|Same as|kept in sync|must match` is a weak proxy for duplication: its hits are deliberate cross-references — per-channel wire shapes, validation strings, doc pointers — so read for the twin rather than grep for it.
- Releases are signed: the Jenkins Release stage runs `bin/sign-release.sh` with the `jclaw-release-signing-key` credential (ECDSA P-256) and attaches `SHA256SUMS.sig`. `jclaw.sh upgrade` and `install.sh` each pin the public half and refuse any release above 0.19.25 that does not verify, the asset-URL overrides being the one deliberate bypass. The upgrader verifies with `utils.ReleaseSignature`, run out of process on the install's `precompiled/classes.jar` alone, so keep that class on the JDK (`ReleaseSignatureTest.theVerifierStandsAlone`); the installer has no trusted class yet and uses `openssl`. Only a missing or wrong signature refuses: a machine without `openssl` is warned and installs unverified, because that is the operator's machine and not something a swapped release controls. `install.ps1` cannot verify at all and warns the same way. The same stage signs `IMAGE_DIGEST`, the digest buildx reports for the image it pushed, since a tag can be repointed and a digest cannot; nothing enforces it: a Docker user runs `docker-pull-verified.sh`, which refuses a missing or wrong signature, only warns where there is no `openssl` as the installer does, and pins `JCLAW_IMAGE` in `.env`, or checks by hand against `release-signing.pub` (INSTALL.md). `ReleaseSigningConformanceTest` holds all four copies of the key equal and tied to the credential.
- Database backup, restore, repair and compaction are one engine, `services.database.H2Maintenance`, behind two doors: the JVM (the Settings panel and `/api/system/database`, which `jclaw.sh backup|db-clean|db-status` also call while the app is up) and `jclaw.sh`'s out-of-process run of its `main` on the H2 and Gson jars plus the compiled classes, which `restore`, `repair` and `compact` always use, stopping and restarting a running instance. Compaction never runs at shutdown, where `jclaw.sh stop`'s kill after 60 s could cut it short. Keep it, `CredentialCopies` and `H2TraceMask` on the JDK, H2 and Gson only — `H2MaintenanceTest.theEngineStandsAlone` pins that — and never let them read the clock: callers pass the stamp.

## Running and verifying

- Backend tests: `play autotest`, never `play test` (it starts an interactive test server). One class, or several comma-separated in one start: `./gradlew playAutotest -Ptests=<Class>[,<Class>]`, about 30 s a start; the full suite takes about 9–10 min. `./jclaw.sh test` runs all five checks to the end and prints a pass/fail summary naming each failed check's `logs/test-*.log`.
- Test sources are the default package: test seams must be `public`. A test class must extend `play.test.UnitTest` or `FunctionalTest`; `TestDiscoveryConformanceTest` fails the build on one that does neither, which the runner would never reach. A test reaches a package-private method by reflection (`SubagentRunEventsTest` into `SubagentRunStore`), so changing such a signature compiles and fails only when that class runs: `git grep -n '"<method>"' -- test` first.
- Never pipe the suite (`| tail` returns tail's exit code); redirect to a file and check `test-result/*.failed.html`. Never compile while a run is in flight; `jcmd -l | grep -E "playAutotest|FirePhoque"` first. A `compileJava` that printed `UP-TO-DATE` measured nothing: `--rerun-tasks` when the compile is the evidence.
- Test classes run concurrently in one JVM: never flip a process-global without its lock (`LuceneTestSync`, `ShellSandboxSync`, `ToolRegistrySync`, `TelemetryTestSync`, `LoadTestHarnessSync`, `SlackWebApiTestSync`, `JevBreakerTestSync`, `FactoryRunnerSync` for `FactoryProcess.setRunnerForTest`, `ScrapeClientSwap` for `WebScrapeTool.CLIENT` and `RobotsCache`, and `ScrapeConfigGuard` for the scrape config keys, taken after `ScrapeClientSwap`; `CompactionTriggerSync` for the `chat.compaction.*` trigger keys and the history limits); scope shared-table assertions to your own rows; a "seeded row missing" red is usually the `Fixtures.deleteDatabase` race, not a regression. Circuit breakers live in a process-global registry keyed by provider or MCP server name, so a test that drives `chat()`, a stream or `callTool` mints its own name and `CircuitBreakers.remove`s it — never `test-provider`, which another class may be tripping. A registered provider is as global: `ProviderRegistry` keeps it cached 60 s past `Fixtures.deleteDatabase`, where a later class's agent naming it, as its provider or fallback, still reaches it, so seed one at `http://127.0.0.1:1/v1`, never a real host, and a functional class unregisters its own in `@AfterEach` (delete the keys, then `ProviderRegistry.refresh()`). Likewise no inbound fixture may carry a real Slack file URL or a WhatsApp access token: the reply or download would reach Slack or Meta.
- In a FunctionalTest, seed what your own HTTP request reads with a `commitInFreshTx` helper — each class keeps a private copy (e.g. `ApiAttachmentsControllerTest`) — because the body is already in a transaction and `Tx.run` joins it. Real HTTP against the autotest server 401s `password_unset` until `AuthFixture.seedAdminPassword` runs; the loadtest harness adds a warmup turn.
- Frontend: `cd frontend && pnpm test` after edits; `pnpm typecheck` is the TS gate, the LSP's `.vue` import errors are false. After a dependency bump, `rm -rf .nuxt node_modules/.vite && pnpm exec nuxi prepare` before believing a green. In a fresh worktree run `pnpm install` first (its postinstall runs `nuxt prepare`); after a lone `rm -rf .nuxt`, run `pnpm exec nuxi prepare` or every vitest file fails at transform.
- `pnpm test --coverage`, never `pnpm test -- --coverage`, which passes with no coverage. `pnpm test` never runs e2e; `./jclaw.sh e2e` needs a live instance answering `/api/status`.
- The live-browser tests in `PlaywrightToolTest`, `JevRunTest`, `StealthFingerprintTest` and `StealthNetworkScreenTest` run only under `JCLAW_PLAYWRIGHT_TEST` (the two stealth classes also need `uv` and Patchright's Chromium), and only `./jclaw.sh test` sets it — it exports `1` when a `chromium_headless_shell-*` build is cached (`PLAYWRIGHT_BROWSERS_PATH`, else the platform cache), adding about 2 minutes, and otherwise prints one skip line. So `play autotest` and `./gradlew playAutotest -Ptests=PlaywrightToolTest` come back green having run none of them: export the flag yourself for a targeted run, or where Chromium lives outside those caches. `0` and `false` opt out; pre-push inherits whatever `./jclaw.sh test` decides.
- Pre-push runs a wildcard-import grep, `spotlessCheck` and `compileJava` before the suite: `./gradlew spotlessApply` after any import-moving change. A pre-commit `.distignore` warning on a new `app/**.java` or test file is expected — dist ships precompiled — don't edit `.distignore`.
- `compileJava` and `compileTestJava` run javac's doclint reference check, so a Javadoc `{@link}`, `@see`, `@param` or `@throws` in `app/` or `test/` that does not resolve fails the build with `reference not found`: link a class the file does not import by its fully qualified name, and after moving a method, fix the links that named its old class.
- Jenkins runs Sonar and coverage but never lint, typecheck or e2e; its release notes are the commit body only when the subject is exactly `Release vX.Y.Z`, which `/deploy` writes. `/deploy` pushes the version's signed tag only once that commit's build has passed, and the Release stage's `gh release create --verify-tag` refuses a version without one.
- Bumping the fork is two-sided: `.play-version` and `/opt/play1` at the same tag, rebuilt (`framework/src/play/version` is a build artifact); a mismatch fails Gradle configure, which pre-push reports as "spotlessCheck failed without reporting format violations".
- Detect a running instance with `./jclaw.sh status` or `lsof -nP -iTCP:9000 -sTCP:LISTEN`, never `ps | grep` (the ~34 KB classpath in its argv matches almost any pattern) and never bare `lsof -ti :PORT` to kill (it matches the app's own client sockets).
- A production start keeps the JDK's AOT cache current (`aot_prepare` in `jclaw.sh`; the Docker `CMD` calls it as `jclaw.sh aot-cache`): when the JDK, the JVM options or the jars changed, it first trains a cache with a full start and stop of the real instance on spare ports (`BACKEND_PORT` + 1000 up, so 9000 and 9443 stay dark), and it never uses one on a JDK without JDK-8377932's fix (25.0.4, 26.0.2, 27), where a stale cache serves old library classes. A changed application class is still loaded fresh, so a code-only restart keeps the cache. `JCLAW_AOT=off` starts without one.
- A broken `test/` class fails `./jclaw.sh dist|bundle`: precompile compiles tests without running them.

## Writing tests

- Assert the outcome a caller or the operator sees, exactly: `assertEquals` on the returned value, the response body or the rendered text, not "contains", "not null" or "did not throw". `SecretRedactorTest` checked that a secret was gone and passed while the mask ate the rest of the line or stopped short and leaked the tail (JF-17).
- Cover the behaviour, not only the bug in hand: the success path, each failure path (refused, missing, malformed, the upstream down) and both sides of every limit (`n` and `n + 1`, empty and one). `use-bulk-select.test.ts` had three tests for JCLAW-1221 and none showing that cancelling the confirmation deletes nothing.
- A bug fix starts with a test that fails on the unfixed code; say in the commit body that you saw it fail.
- Choose the layer by what the behaviour crosses: pure logic, a `UnitTest`; a route, a controller or the database, a `FunctionalTest`; a composable or component, a vitest file under `frontend/test/` that drives it as a page does (mount, act, assert the request sent and the state shown); a journey across pages, one Playwright spec under `frontend/tests/`.
- Stub only what crosses a process or network boundary (`HttpFactories.runWith`, `registerEndpoint`, a `*ForTest` seam), never the code under test: a test that stubs what it checks passes whatever the code does.
- Name a test after the behaviour it pins (`cancellingTheConfirmationDeletesNothing`), so a failure says what broke.

## Conventions that differ from defaults

- Config keys live in the Config DB; document an unseeded key in `conf/application.conf`, and never seed a key whose absence already means "off".
- `git grep -P`, never `-E`, for `\b`, `\d`, `\s` — macOS `git grep -E` drops them silently and matches nothing.
- Frontend API writes go through `useApiMutation().mutate` or inside `useSaveAttempt().attempt`, never a bare `$fetch` with a write method (`useSettingsConfig.ts` is the one allow-listed store): the ESLint rule `jclaw/no-bare-write-fetch` fails the lint on a literal method, but not on one held in a variable. A handler read issued with a bare `$fetch` whose key can change mid-flight takes a `useLatestRequest()` token and returns if it is stale; `useFetch` refetches are already aborted by Nuxt. The Settings store's `refresh()` keeps the last good copy on failure, so call it after a failed write too.
- `jclaw.sh` targets macOS bash 3.2 under `set -euo pipefail`: brace an interpolation before a non-ASCII character, guard a command substitution that can fail (`$(cmd || true)`), use an `EXIT` trap rather than `ERR`.
- New tool names are `<singular_noun>_<verb>` (`conversation_send`, `subagent_spawn`); older names such as `generate_image`, `task_manager` and `exec` predate the rule and keep their names.
- pnpm applies no release-age gate to frontend deps (`minimumReleaseAge: 0` in `frontend/pnpm-workspace.yaml`; Renovate's own 3-day delay still applies): gate a bump on compile and tests, pin Nuxt exactly, and smoke `nuxt dev` on a Nuxt bump.
- A Settings panel reads a sidecar-status endpoint with `useLazyFetch`, never a top-level `await useFetch` — it cold-boots the sidecar and suspends the panel. A test that remounts a page with a different fixture for the same URL calls `clearNuxtData()` in `beforeEach`: `useFetch` caches by URL across mounts. Never add a `uv.lock` gate for the sidecars.

## Known pitfalls

- Never `Thread.interrupt()` or `Future.cancel(true)` a thread that touches H2/JPA: the JDK closes the FileChannel and the file DB dies; use a volatile flag. `db.url` opens the file through H2's `retry:` file system, which reopens a channel an interrupt closed (JF-15): that is the net under this rule, not permission to interrupt. Never park many virtual threads on timed waits (JDK-8373224): schedule on a small platform-thread executor and block on an untimed `get()` — `ChannelTest.noRetrySchedulerFutureIsAwaitedWithATimeout` fails a timed wait on a `RetryScheduler` future.
- A job Play schedules (`@Every` or `@On`) extends `jobs.PeriodicJob`, not `Job`: H2's exit hook closes the database at SIGTERM while Play still drains HTTP and fires jobs, and the base skips a tick from then on and reports one the shutdown cut short in one INFO line (JF-23); `PeriodicJobConformanceTest` fails a scheduled job that extends anything else.
- A pool drain destroys the H2 in-memory test DB with its last connection; hold one connection across it (`TelemetryDataSource.switchTo` is the reference).
- A new NOT NULL entity column needs `@ColumnDefault` — the ALTER fails on populated rows, and the test DB (`%test.jpa.ddl=create`) never sees it. Raw-connection DDL must `commit()` explicitly; Hikari runs `autoCommit=false`.
- `Result` is a `RuntimeException`: a render inside `try {…} catch (Exception)` is swallowed into a 500 — assign in the try and render after it, or rethrow with `catch (Result r) { throw r; }` ahead of the broad catch.
- Retention is one resolver, `jobs.RetentionDays`: absent or blank → the caller's default; 0 or negative → `DISABLED`, and the job returns before it computes a cutoff — never a window, since a cutoff at or after now takes the whole table; over the caller's ceiling or non-numeric → the default plus a warn. The ceiling stays per-caller: the event log passes `NO_CEILING`, the rest 3650. `ConfigService` refuses `logs.retentionDays` below 1 and Settings pins `:min="1"`, so for that key the non-positive branch is a net for a value written around the API; `tasks.retentionDays` offers 0 as off.
- `Model.find().fetch()` is untyped (`<T> List<T>`, `T` inferred): copy elementwise. Fix a lazy N+1 with `@BatchSize`, not a manual IN query. `FunctionalTest` has no PATCH helper.
- A media bearer addresses its message by position (`chatMessageIndex`), and `CompactionGate` (rebuilds the list from the persisted rows) and `ContextWindowManager`'s drop-oldest branch (shifts every survivor down) replace the list under it: apply a media rewrite after both, through their `MessageHydrator.Hydration`-taking overloads, which return bearers matching the list each produced — never before compaction, which discards anything written earlier. Pruning, compression, tool-result truncation and `CurrentTimeInjector` are index-preserving. `VisionAudioAssembler.holdsUserTurn` skips a slot that is out of range or not `USER`, so a missed re-base skips the rewrite rather than throwing.
- `ContentTypeDetector.isCode` routes to `CODE` only when `CodeCompressor.detectLanguage` (which returns on the first hint that matches) finds a language and there are two hint-carrying lines, or at most five non-blank lines in total; `JS_HINT` still answers JAVASCRIPT for any line beginning `export `, so the signal count, not the hint, keeps prose out of `CODE`. Bias toward TEXT: misrouting code costs compression quality, misrouting prose costs the content. Pin JavaParser at `BLEEDING_EDGE`, not its `JAVA_11` default, so a dependency bump cannot leave the parser a release behind; share the `ParserConfiguration` and build a `JavaParser` per call — the instance is not thread-safe, the configuration is.
- Bulk and cascade deletes skip `@PostRemove` and orphan Lucene docs — evict explicitly. A Lucene codec-boundary bump: wipe `data/jclaw-lucene/` while pre-v1 rather than add backward-codecs, and verify through the live search endpoint.
- New ArchUnit rules reuse `ArchitectureTest.APP_CLASSES`, which imports `build/classes/java/main` — never the running JVM's `CodeSource`, where stale precompiled bytecode under FirePhoque manufactures violations.
- "Zero call sites" is not dead code: a retention Javadoc, `@SuppressWarnings("unused")` or a reflection test marks a deliberate keep. Drop an applied `renameKeyIfPresent` call site, keep the helper.
- `graphify update .` re-clusters whenever the code graph changed and names each community after its highest-degree node, so the `community=` in query output is a hub (`.get`, `okhttp3.OkHttpClient`), not a description. Nothing is curated, so nothing is lost by running it.
- JCLAW acceptance criteria forward-reference helpers and tickets that were never built: verify before designing around them.
- `memory.jpa.vector.queryPrefix` and `memory.recall.minCosine` move together. A CSP, if enabled, must allow `'unsafe-inline'` for `script-src`; Nuxt inlines `window.__NUXT__`.
- A task with both `Task.modelProvider` and `Task.modelId` set fires on that model (`AgentRunner.runForTask` applies it as the stub conversation's override); an unpinned task, or one pinning an unconfigured provider, follows its agent's current model.
- Layout tests run at phone width: `test/setup.ts` stubs `matchMedia` to match nothing, so the sidebar starts closed and its desktop-only markup never renders; stub `(min-width: 1024px)` to `true` in the test (`frontend/test/layout-brand.test.ts`).
- JClaw has two trust axes. **The agent principal:** an unscoped `findById` on an `OPEN` or `OPERATOR_ONLY` route is not IDOR, and `/api/providers`, the config reads and the channel list are agent-reachable on purpose — fix a leak there at the seam (`SsrfGuard`, `ConfigService.maskValue`, the dangerous-verb gate), never by closing the endpoint.
- Every routed `/api` action declares `@AgentAccess`: `OPEN`, `OWN_ONLY` or `OPERATOR_ONLY`; no annotation means `OPERATOR_ONLY`. Every auth interceptor calls `AgentAccessGate.enforce()`, which refuses the agent principal before an `OPERATOR_ONLY` action runs, and `JClawApiTool` advertises and calls only the other two levels — so put no operator guard in an `OPERATOR_ONLY` body, and never reintroduce `@ChatHidden`, `@AgentCallable`, `PATH_BLOCKLIST` or a hidden-but-reachable route: a route an agent should see is `OPEN`, otherwise it is refused.
- A mutating `OPEN`/`OWN_ONLY` action names what bounds it in a non-blank `reason`, and an `OWN_ONLY` action reaches `RequestPrincipal.mayReachAgentScopedRow` (a row route 403s) or `callingAgent` (a list route pins its query to the caller); `CapabilityRulesTest.everyRoutedApiActionDeclaresAnAgentAccessLevel` fails the build otherwise. Widening what an agent can invoke means editing the pinned list in `JClawApiToolTest.theCallableApiSurfaceIsExactlyTheseRoutes`.
- A `GET` route's `@ApiResponse` type carries no credential-named `String` — expose a `hasX` boolean, as the channel binding views do. Give a new `GET` a declared response type rather than adding it to `CredentialReadGateConformanceTest.UNCHECKABLE_GET_ROUTES`, and delete a line from that list once its route declares one.
- Read the calling agent from `RequestPrincipal.callingAgent()` and its turn's origin from `callerOrigin()`, never from a request field: `JClawApiTool` stamps `X-JClaw-Agent-Id` from the `Agent` it is handed and `X-JClaw-Caller-Origin` from `DangerousActionGate.effectiveOrigin`, never from the model's arguments, and both count only on an agent-originated request. An unstamped bearer is an unidentified agent, which `OWN_ONLY` refuses.
- `POST`/`PATCH /api/tasks` only record or lower a task's fire-time origin to the caller's; only the operator's `POST /api/tasks/{id}/trust` raises it.
- The operator and `main` reach every row (`isOperatorOrMainAgent`); any other agent reaches only its own conversations and their messages, subagent runs (by `parentAgent`) and scrape jobs (by `agent`) — `main` sees down the tree, nothing sees up or across. Every other `OPEN` route, `/api/tasks` included, is instance-wide.
- Bound a dangerous argument or field instead of closing its route: `services.printing.PrintTargetGuard` keeps `host`/`port` open but refuses link-local, multicast and `0.0.0.0`, and makes `PrinterTool.dangerous(args)` true for an address that is neither a discovered printer nor the saved default; MCP CRUD stays `OPEN`, but `requireMainForStdio` limits a `STDIO` transport — an unsandboxed `ProcessBuilder` outside the shell allowlist — to the operator and `main`, checked against the row's effective transport on update; `requireOperatorForAcpChange` refuses an agent flipping `acpAllowed`.
- `jclaw_api` gates the parsed `HttpUrl.encodedPath()`, never the model's string, and refuses `#`, a backslash, `//` and dot-segments before parsing; keep both, or `..` (or `%2e%2e`) resolves past the gate and out of `/api/` into the `{controller}/{action}` catch-all.
- Serve a workspace file with `Content-Security-Policy: sandbox` always, and as `attachment` unless it is a raster image (never SVG), audio or PDF — there is no global CSP, so the response carries its own.
- **The channel sender** is the other trust axis, independent of the agent principal: a turn is owner-initiated only when its sender id equals the binding owner's — Telegram, and Slack once `ownerUserId` is set, DM or group alike. A non-owner group member, every WhatsApp sender and every user of an owner-less Slack binding are guests. `DangerousActionGate.withOwnerInitiated` binds it in `TelegramInboundTurn` (webhook and poller), `TelegramReactionNotifier.handleReaction`, `SlackInbound`, `ScrapeJobService`'s and `TaskRunReports`' completion turns (which re-bind the value captured at submit) and `QueueDrainOrchestrator.runOwned` (which re-binds the value each `QueuedMessage` recorded at enqueue, and a guest's for a batch holding one); `ownerInitiated()` reads it, and unbound means guest — never default it to true. Web chat and voice mode are the operator's origins (`ChannelOriginTrust`). A hosted app (`app`) needs the signed-in session as they do, but its bundle writes the message text, so it is not one.
- A standing tool-approval grant is spendable only on an owner-initiated turn or one whose effective origin classifies as `OPERATOR` — its key `(agentId, toolName)` carries no channel. `jclaw_api` takes the narrower `DangerousActionGate.ownerReadsAlone` (an operator turn outside a group chat; a fire passes by `AgentRunner.fireOffersOwnerTools`): failing it, the tool is neither offered (`ToolRegistry.turnDisabled` and `forTurn` at every prompt and tool-list site) nor callable, and `ParallelToolExecutor` refuses a tool the turn was not offered before the gate, so no such call asks the owner. `Commands.execute(…, ownerInitiated)` refuses `/subagent`, `/prompt` and the `/model` write forms to a guest (they reach every subagent run, the operator's prompt library and the conversation's model); every other command stays open, and web chat passes `true` because it sits behind `AuthCheck`. A Slack binding with no `ownerUserId` refuses those commands to everyone, the operator included — configure the owner rather than file a bug. `/subagent info|log|kill` is deliberately not scoped to the calling agent's runs: one operator owns every agent.
- `TelegramReactionNotifier.reactorAllowed` drops a private-chat reaction whose `reactorId` is not the owner: a DM peer id resolves to the owner's conversation and the default `own` policy admits every DM reaction, so a stranger's reaction would otherwise run a turn over the owner's history and receive the reply. Group reactions keep `shouldNotifyReaction`. Label reaction text `[reaction]`, never `[system]` — the reactor chooses their own display name.
- `DangerousActionGate.hasStandingGrant` ORs a never-pruned in-process set with the `tool_approval_grant` table, so deleting the row alone fails open: pair every `ToolApprovalGrant.revoke` with `DangerousActionGate.revokeGrant`, and an agent delete (its rows go by `ON DELETE CASCADE`) with `revokeGrantsForAgent`. The row's granting channel and peer are provenance only; the gate never reads them. Escape approval prompts per grammar: Telegram `escapeHtml` (`& < >`); Slack `SlackMarkdownFormatter.escape` plus a zero-width space after each backtick, or a model-controlled argument closes the code fence and renders the rest of the prompt as mrkdwn. Leave `*` and `_` unescaped — Slack has no escape for them, and the block structure is what matters.
- A persona file (`SOUL.md`, `IDENTITY.md`, `USER.md`, `BOOTSTRAP.md`, `AGENT.md`) reaches the prompt only at its approved version (`services.PersonaFileApprovals`, JF-136). `WorkspaceFiles.writeWorkspaceFile` is JClaw's own write and approves one; a tool writing for the agent, a download or a scrape, uses `writeAgentFile`, which approves nothing, so a persona file it lands on waits for the operator. A JClaw edit to existing text goes through `applySystemEdit`, which edits the approved and the on-disk text apart, so an agent's pending change is never approved with it. A new tool that brings no outside text into the conversation overrides `Tool.readsOutsideContent`: the default `true` keeps every later persona edit in that conversation waiting for the operator, as a prompt that carried a memory resting on someone else's words does. The filesystem tool approves only the text its write made, and an append or edit only on top of the approved version.
- A model-chosen destination whose legitimate targets are loopback or the LAN (a printer `host`, a provider or MCP URL) is screened with `SsrfGuard.isBlockedForProvider`, never `isUnsafe`, which also blocks loopback and RFC-1918; a web URL the model browses, fetches or scrapes stays on the strict `assertUrlSafe`/`SAFE_DNS`. A per-attempt failure string returned to the model never carries the transport exception — "refused" versus "timed out" is a port scan — so `PrintDispatcher` returns `<protocol>: no response` and keeps the detail on `EventLogger.warn`.
- Parse a URL the page supplies (a `Location`, a harvested href, a sitemap entry, the browser's final URL) with `utils.Urls`, which percent-encodes what `URI` rejects and browsers send raw after the authority; keep a URL an operator or the model typed on `URI.create`, so a typo fails at the edge with a message naming it. `SsrfGuard`'s own parse is always `Urls`, so the guard reads the host the fetcher sends.
- The installer paths (Playwright Chromium, `uv run`, the JRE download) were audited and accepted on 2026-08-28; do not re-flag them.
- The release bundle and the Docker image ship neither Playwright's `driver-bundle` (all-platform Node.js, ~194 MB) nor Chromium. `build.gradle.kts` filters the jar out of `playBundle`'s `playClasspath`, so it is in neither the bundle's `lib/` nor its `.classpath`; on the first browser call (or from Settings → Browser) JClaw downloads its platform's official Node.js, verifies it against the SHA-256 pinned in `services.browser.PlaywrightNode`, hands it to Playwright as `PLAYWRIGHT_NODEJS_PATH` in `Playwright.create`'s env map, then installs Chromium. Dev, tests and `play run` keep `driver-bundle` on the classpath. Docker puts both downloads on the data volume (`data/playwright-node`, `PLAYWRIGHT_BROWSERS_PATH=/app/data/pw-browsers`) so an image upgrade does not re-fetch them. Do not re-add a Chromium image stage: Playwright 1.63 installs at container runtime on the ubuntu:26.04 base on arm64 and amd64 (measured 2026-09-24).
- Because that volume outlives Playwright bumps, "is Chromium installed" is revision-exact (`BrowserSetup.chromiumInstalled`: an `INSTALLATION_COMPLETE` marker at each `browsers.json` revision), never "any `chromium*` directory". On a Playwright bump `PlaywrightNode.VERSION` must equal driver-bundle's `node --version` (`PlaywrightNodeTest.thePinnedVersionIsTheNodeThatDriverBundleShips` fails until it does); re-pin the five hashes from that release's `SHASUMS256.txt` — no test checks them. The chat's progress bar starts from the `Using tool: browser` status frame, because the `tool_call` frame arrives only after the call returns.
- A subagent run has one parent: the conversation that started it, or the task run when a task fire did (`SubagentRun.parentTaskRun`), never both. `ToolContext.taskRunId() != null` means there is no parent chat, so never resolve one by recency there (`DeliveryResolver.operatingConversation` falls back to the agent's latest conversation, which filed task-started runs under an unrelated chat). A fetch join on a run's parents is `LEFT`; `codingrun.step` names a `conversationId` only for a chat-started run, and the chat adopts a run by that id alone.
- A fire-started child reads its parent off `AgentRunner.taskFireParent`: the fire's origin as its channel (so `DangerousActionGate` judges it as it judges the fire), the task's pin as its model, and the task's tool list in `Conversation.enabledToolNames`, which every descendant copies. A new place that builds a conversation turn's `ToolDef`s applies `TaskToolPolicy.restrictSubagent` and `ToolRegistry.forTurn`, as the two in `AgentPromptPreparer` do, or a fenced task leaves its fence by delegating. The prompt follows the same list: each place that assembles one for a fire or a conversation turn passes `ToolRegistry.turnDisabled` (the fire, both `AgentPromptPreparer` paths, `CompactionGate`'s rebuild), or its catalogs name tools the turn cannot call. Skills are deliberately not filtered by a list: a task may use part of a skill whose declared tools reach past it. `mode=inline` runs as `session` in a fire, with a `note` in the result, rather than being refused: an error costs an unattended run a round; `context=inherit` grants the tool union without a summary.
- A task run owns the runs it started: `SubagentRegistry.deleteRunsStartedBy` removes them, stopping any in flight, before the task runs go. The database cannot (a run's transcript, Lucene docs and spawned agent are outside any FK), and without it the 10-run cap and retention prune task history while the runs pile up. `ON DELETE SET NULL` on `parent_task_run_id` is only the net for a run that starts mid-delete.
- A run's child agent is not always the run's: a spawn naming `agentId` (its own id included) runs on an operator's agent. Delete an agent with a run only when the spawn created it (`childAgent.parentAgent != null`), and never delete an inline run's `childConversation`, which is the parent chat. `SubagentRegistry.deleteRun` and `ConversationDeletionCascade` are the two that decide; deleting such a run or its chat used to delete the operator's agent, workspace and memories with it.
- `AgentService.delete` ends in `em.clear()`: every entity loaded before it is detached, so re-read by id before `entity.delete()` and load rows inside the loop. `SubagentRegistry.deleteRun` takes an id for this reason.
- A coding run is `SubagentRun.runtime = 'acp'`, set at the insert. `workdir` is set later and stays null for a run refused approval or a folder, so it does not identify one. `resolveAcpWorkdir` throws rather than return no folder: a harness writes outside JClaw's tool confinement, and the server's own directory is the checkout on a source install. `CodingRunMonitor` learns that a run ended only from the live `codingrun.done`, so a view that mounts it afterwards passes `recordedStatus`.
- `CompressionPipeline` runs before every model round, so it sees a tool result before the model does. It leaves an unread result whole (one that follows the last assistant message, up to `chat.compression.firstViewMaxTokens`) and compresses it from the next round on: compressed unread, 30% of large results were fetched back through `ccr_retrieve` in the same turn, 86% for `exec` (measured 2026-10-13 over 45 days), each costing a round and a second full copy; under the rule, 15% for `exec` (2026-10-14 to 10-18). A result the model picks from across rounds declares `Tool.verbatimResult(args)` and is never compressed, since the JSON compressor keeps three entries of a list: `McpServerTool`'s action list, `describe` and resource `read`, and `jclaw_api`'s `discover`. A new catalog-style call declares it too, and caps its size, as `read` does at `READ_MAX_CHARS`: a verbatim result escapes the first-view bound, and `ContextWindowManager`'s tool-result truncation spares the most recent messages (`chat.truncateToolResultsPreserveRecent`, default 4). A large MCP server lists names and one-line summaries (`FULL_CATALOG_MAX_CHARS`), and `{"describe": [...]}` returns the schemas of chosen actions; never return every schema of a large server in one result. Separately, `ToolResultPruner` stubs any large result from an earlier turn whatever an agent's compression setting; a result the model keeps following for the whole conversation (a skill's SKILL.md, through `skill_read` or a `filesystem` read) declares `Tool.keepsResultInContext(args)`, is never compressed, and is kept as Claude Code keeps skills: newest first, each up to `SKILL_KEEP_CHARS` (20,000) within `SKILL_BUDGET_CHARS` (100,000) a conversation, an older copy of the same text stubbed. A SKILL.md therefore stays under 20,000 characters, detail in `references/`; the filesystem tool warns on a save past it.
- `EventLogger.record` masks credentials with `utils.SecretRedactor` before the message reaches the log file or the `event_log` table: agents put keys on `exec` command lines and in tool arguments, and each call is logged twice (`exec: …` and `Executing tool … args: …`). Log anything that can carry a command, a URL or tool arguments through `EventLogger`, never `play.Logger` directly, which bypasses it. The redactor keeps the header or parameter name. A pattern only finds the name; `valueAfter` then follows the quoting to where the value ends (its own quote at the same escape depth, the quoted string it sits inside, or a shell word), because a regex cannot: widening a value's character class is how a tail leaks. Where two readings differ it takes the longer one and over-masks. It tells a count or a cursor from a credential by the name only (`tokens`, `tokenCount`, `page_token`), never by the value's shape. No pass trusts an earlier pass's mask as the end of a value: it scans again, since the earlier one may have stopped short. Its input is model-controlled, so the work stays linear: a pattern's quantifier is bounded or possessive, and each pass reads forward once, for the value and for the quotes before it (`SecretRedactorTest` times 500,000 characters of each trigger, bare and inside one long quoted string). Logged arguments are JSON inside JSON, so a quote arrives behind backslashes and `=`, `&`, `'` also arrive as `\u003d`, `\u0026`, `\u0027`; `aSecretIsMaskedWholeHoweverItsContextEscapesIt` writes a secret the way each context escapes it, and a new context belongs in that matrix. When reading `logs/application.log` or `event_log` rows written before the mask, never print an `exec:` or `args:` line.
- User-guide links are `/guide#<page id>-<slug>`, and an explicit `{#id}` is prefixed the same way (`GuideRenderer.vue`); the guide is simple English with on-screen strings quoted exactly. The instance serves it from the built SPA, so an edit shows after a restart.

## Project Overview

JClaw is an AI-powered automation platform built on **Play Framework 1.x** (Java) with a **Nuxt 4** (Vue 3 + TypeScript) SPA frontend. It combines OpenClaw agent orchestration and JavaClaw job scheduling into a single Java-first platform.

**Status**: pre-v1 (beta), work in progress.

## Setup, commands and hooks

- After every fresh clone (including `rm -rf` + re-clone cycles), run `./jclaw.sh setup`. It wires `.githooks/`, installs the frontend dependencies the pre-commit hook's `lint-staged` needs, and checks that both `origin` (Bitbucket) and `github` remotes exist: `core.hooksPath` lives in `.git/config` and `frontend/node_modules/` is gitignored, so no clone carries them. Without it the hooks silently don't fire and `/deploy` fails on the github push.
- `play run` serves the backend on :9000; `cd frontend && pnpm dev` serves the SPA on :3000 and proxies `/api/**` to it. The frontend's scripts are in `frontend/package.json`.
- `./jclaw.sh e2e` runs the Playwright suite against whichever mode is listening, with `JCLAW_ADMIN_PASSWORD` from `certs/.env`. It is local UAT, not a gate, and stays out of `./jclaw.sh test` because it needs a live server.
- `pre-commit` runs `lint-staged` (ESLint and Stylelint `--fix`) over staged `frontend/**` files and re-stages what it fixed: fix what it cannot and commit again, and if a rule is wrong, fix the rule rather than bypass it. `pre-push` runs only the backend test classes the push reaches (`bin/select-tests.mjs`), and the frontend checks only when a frontend input changed, cached per HEAD across the two remotes; Jenkins runs the full suite on every push, so its failure is an integration failure to fix, not a flake to rerun. A push publishes to both — which is why only `/deploy` pushes, so a release is a deliberate act rather than the side effect of finishing a task. `post-checkout` seeds a new worktree's `certs/.env` and `PLAY_TEST_PORT`. The hook bypasses in [DEVELOPMENT.md](DEVELOPMENT.md#git-hooks) are for a human, never an agent.

## Architecture

### Backend
- **Play 1.x** conventions: controllers are static methods in `app/controllers/`, models in `app/models/`, views (Groovy templates) in `app/views/`
- Routes defined in `conf/routes` — uses Play's `{controller}.{action}` catch-all pattern
- Configuration in `conf/application.conf` — supports environment prefixes (`%prod.`, `%test.`)
- Dependencies managed via `build.gradle.kts` using the `org.playframework.play1` plugin from the `/opt/play1` fork. `settings.gradle.kts` resolves that plugin from a flat `file:///opt/play1/framework/gradle-plugin-repo` Maven repo — **not** `includeBuild("/opt/play1")`, which builds the plugin from source and needs write access into the fork, so it fails on read-only installs. The plugin version is read from the installed fork's `framework/src/play/version`, and `build.gradle.kts` cross-checks that against `.play-version` (plus a pinned range), failing the build on drift. To bump the fork: edit `.play-version` **and** check out the matching version in `/opt/play1`.
  - Consequence: `/opt/play1` is a separate root build with its own Gradle wrapper, so builds there start their own daemon.
- Tests in `test/` — JUnit 6 (Jupiter 6.1.3, bundled by the play1 fork in `framework/lib`), extending Play's `UnitTest` or `FunctionalTest`
- Test mode uses H2 in-memory database (`%test.db.url` in application.conf)

### Frontend
- Nuxt 4 SPA in `frontend/` with Tailwind CSS v4
- API proxy: dev requests to `/api/*` are forwarded to the Play backend via Nitro devProxy (see `frontend/nuxt.config.ts`)
- Reads use Nuxt's auto-imported `useFetch` / `$fetch`, with `fetchParsed` in `frontend/composables/useApiParsed.ts` for schema-validated reads (JCLAW-287); writes go through `useApiMutation` or `useSaveAttempt`, and the lint fails a bare write `$fetch`
- Package manager: **pnpm 12+**, pinned in `frontend/package.json`'s `packageManager` field. To bump the pin: `cd frontend && pnpm self-update <version>`, then commit `frontend/package.json` **and** `frontend/pnpm-lock.yaml` — the lockfile carries the new binaries' integrity. The reasons, and the Node 25+ test flag: [frontend-toolchain.md](docs/agents/frontend-toolchain.md).

## graphify

Optional codebase knowledge graph, installed per-machine with `uv tool install graphifyy` (the CLI is `graphify`). Build it with `/graphify .`; `graphify-out/` is gitignored, so the graph is local to each clone and never committed.

This project has a knowledge graph at graphify-out/ with god nodes, community structure, and cross-file relationships.

When the user types `/graphify`, use the installed graphify skill or instructions before doing anything else.

Rules:
- graphify answers structural questions about a symbol you can already name: what uses it, what it touches, how two things connect. It matches your words against node labels and file paths — class, method and file names, markdown headings — never against code bodies or comments, so it cannot find a symbol from a description: get the name with one grep first, then expand it here. It is the preferred first step for those questions, not a gate. The Claude Code hook's "MANDATORY" reminder never blocks a read or a search, and an edit to a file you already know needs no query.
- Use the narrowest command. `graphify affected "name()"` lists what calls, imports or extends a symbol, with `file:line` — about 500 characters for `load3Dmol()`, where `graphify query` returns 17,000; name a method with its `()`. `graphify explain "Name"` is one node and its direct connections, and the way to look up a file name. `graphify path "A" "B"` links two symbols; add `--undirected` when it reports no directed path. `graphify query` returns the two-hop neighbourhood: reach for it last.
- Give `graphify query` exact identifiers and nothing else: `graphify query "load3Dmol acquireViewer"`, never a sentence. Every word that is not a stopword seeds its own traversal, so a question starts from a dozen unrelated hubs — on three of four test questions here a sentence returned 0–8% on-topic nodes and the symbol name 72–98%. Identifiers are not split on camelCase, so type them whole; a punctuated file name splits into several terms. "calls", "imports", "returns", "fields" and "parameters" each silently restrict the walk to that edge type (`who calls RetentionDays` returns one node), so leave them out or say `--context call`. `--budget N` lifts the 2,000-token cap when the output starts `TRUNCATED`.
- If graphify-out/wiki/index.md exists, use it for broad navigation instead of raw source browsing.
- Read graphify-out/GRAPH_REPORT.md only for broad architecture review or when query/path/explain do not surface enough context.
- After modifying code, run `GRAPHIFY_NO_BACKUP=1 graphify update .` to keep the graph current (AST-only, no API cost). Without the variable every run that changes the graph leaves a dated ~70 MB copy of the previous one in `graphify-out/`.

## Behavioral Guidelines

### 1. Communicate Concisely

**Direct answers. Digestible nuggets. Progressive exchange.**

The user is tracking the work as it happens, not reading a report at the end. Make it easy to follow.

- Lead with the answer or the action. Skip the preamble. The user can ask for more if they want it.
- Break multi-step work into small confirmable units rather than dumping a full multi-stage plan up front. Each step's outcome may change the next; don't pre-commit to plans the user hasn't seen the inputs for.
- After each meaningful step, state in one or two sentences: what just happened, what's next, what (if anything) is blocked. So the user can track progress without re-reading prior messages.
- Match response length to the size of the question. A one-line ask gets a one-line answer. A multi-step refactor gets the diff summary plus a "next step" hint, not a five-paragraph essay.
- Keep insights and tangents brief. If a longer explanation might help, offer it ("want me to expand?") rather than emitting it by default.

The signal you're getting this right: the user can scan your message in seconds and know exactly what state things are in.

### 2. Know What Is Verified

**Separate what you ran from what you inferred. Say which is which.**

- **Claims about external systems need the external system.** How Slack renders an audio attachment, what a provider's API accepts, whether a client plays a codec — these are facts about someone else's software, and reading docs or reasoning from adjacent behaviour is inference, not verification. Infer freely; just label it, and don't let an inference reach a commit message or a ticket as fact.
- **A green result you did not scope is not evidence.** A quality gate can pass because nothing was measured; a test can pass because its fixture avoids the interesting case. Before reporting a pass, check that the thing you care about was actually exercised.
- **Validate a measurement harness against a known-zero case** before trusting a number it produces. Time a no-op; assert on an empty input. A harness that reports plausible nonsense is worse than no measurement, because it gets believed.
- **A flake is a defect until proven environmental — and "environmental" means naming the mechanism.** "Re-ran and it passed" is not a diagnosis. There are known interference cases here (a live app on the test port, parallel worktrees); those are identifiable by name, and anything else is a real failure.

### 3. Reach For What Exists

**Instrumentation, helpers, and prior verdicts already in the repo beat improvising.**

- Latency questions have `LatencyStats` / `LatencyTrace`, `/api/metrics/latency`, the `./jclaw.sh loadtest` harness, and JProfiler. Prefer them over a hand-rolled stopwatch.
- Before deciding a static-analysis finding, check how the same rule was already resolved elsewhere in this project. A verdict that contradicts an established one either needs to change both places or is wrong.
- Match the existing construction for test fixtures and helpers (`AgentService.create`, `commitInFreshTx`, the probe `setForTest` seams) rather than building a parallel one.

### 4. Comments Carry Reasoning, Not Narration — Tersely

**Never write a comment that restates the code. Default to no comment; when one is warranted, default to one line.**

Redundant commenting is the most common defect in agent-written code, and the pull toward it is strong enough to survive a general instruction to stop. So this section is checks and examples rather than adjectives — apply it mechanically, not by feel.

**The delete test — run it on every comment you write.** Delete the comment and re-read the code. If the code still conveys everything the comment did, it stays deleted. A comment survives only by carrying what the code cannot: a reason, a constraint, a measurement, or a bug.

**Never write these:**

```java
// Loop through the discovered printers        ← restates the next line
for (var p : printers) { ... }

// Added image types (JCLAW-911)               ← changelog; belongs in the commit message
// Now also deletes the transcode cache        ← narrates your change, not the code
// This is important because...                ← if it needs a paragraph, fix the code
// TODO: could be faster                       ← aspirational; open a ticket or delete it
```

**Write these:**

```java
// Canon rejects text/plain outright — negotiate the format before sending.
// A4 job against a Legal tray reports as spool-area-full, not as a size error.
// JIPP is Kotlin: getStatus() is @NotNull, so a null guard here is dead code.
```

**A comment earns its place only by recording one of:**

- why the code is this way and not the obvious way — name the ticket, benchmark, or bug that decided it
- a non-obvious invariant or precondition a caller has to hold
- the specific failure a guard prevents
- an external contract the code cannot state itself: wire format, provider quirk, library nullability

**Length follows the code around it.** Match the density of the comments beside yours: a new entry in a list of one-line comments gets one line. A longer comment is right when each line carries something a reader would otherwise get wrong; one that needs a paragraph to justify a workaround usually means the code should change instead. In the Settings banner's prefix list (`managed-prefixes.ts`), `playwright.`, `jtokkit.` and `memory.` run several lines because one is a deliberately-retained retired namespace and the other two cover keys written autonomously by a job — all genuinely surprising. Every ordinary entry beside them is a single line, and a new one that isn't will be sent back.

**Javadoc is held to the same bar.** Stating a public contract — parameters, return, thrown conditions, threading — earns its length. Prose rationale *inside* a Javadoc block does not: it faces the same delete test as any other comment, and a private helper usually needs no Javadoc at all. A ten-line block explaining why a two-line method exists is the same defect as a ten-line inline comment.

**Provenance for a *change* belongs in the commit message, not the code.** "Why this must stay" is a comment; "why I added this" is history. Explaining the bug you just fixed, in the code that fixes it, duplicates the commit body and ages into noise within one refactor.

**During refactors, comments move with the logic they explain.** A comment recording *why* a check exists is frequently the only surviving record of a bug that was actually hit, and deleting it as clutter is how the bug comes back.

### 5. Commit Messages Are Public

`/deploy` pushes to **both** remotes, and the GitHub mirror (`github.com/tsukhani/jclaw`) is **public**. Commit bodies, tags and release notes are published artifacts, not internal notes.

Write them factually: what changed, why, what was verified. That is also what makes them useful internally — the constraint costs nothing. Keep genuinely internal material (credentials, customer specifics, unreleased commercial plans) out of them entirely.
